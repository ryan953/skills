The main structural finding: the corpus is bimodal

The anchor rate is not uniform. It is 9% on the PRs you write and 73% on agent-authored ones. So issue → RCA → description → code is not uniformly sparse. It is fully populated on exactly the agent-authored PRs, and near-absent on your hand-written ones.

The classifier should route on that instead of running one uniform pipeline. The agent-authored slice is where it earns the most, because every rung exists there — and that is the same slice you want auto-labelled as correct and proper rather than sent to a human.

The chain itself still needs the adjustment I proposed: keep it, but treat each rung as optional and grade only the pairs where both rungs exist. A missing anchor is a skip, not a penalty.

The rebase guard

A rebase rewrites a commit's committedDate. Without a guard, work you authored before feedback looks like a response to that feedback. Comparing authoredDate against committedDate catches it. The guard fired on 27 of 299 PRs, and 11 of those would otherwise have flipped from "never responded" to "responded".

2 Cache the corpus

One script, scripts/harvest.mjs, written with zx. It runs three gh search queries for the PRs you wrote, reviewed, and commented on. Then it makes one GraphQL call per PR.

I tested that call. It returns the metadata, every commit with its timestamp, every comment, every review with its inline comments, the linked issues, and the close event actor — about 3.5 KB for a small PR.

~/.cache/pr-classifier/
  prs/<owner>__<repo>__<num>.json    # raw payload
  diffs/<owner>__<repo>__<num>.diff   # lazy: only if the PR reaches stage 3
  index.json                          # slim rows for fast iteration
  labels/gold.jsonl                   # hand labels for the eval

A PR is re-fetched only when its updatedAt changes. The diff is never fetched during the harvest.

Exclude the cleanup bot

Drop the PR when the close event actor is getsantry, or when a getsantry comment says the PR "has gone three weeks without activity". That is the exact wording in your corpus.

Filter the other bots, but mine two of them

These logins post on your PRs and none of them are feedback: github-actions, linear-code, cursor, codecov, sentry-io, seer-by-sentry. If you leave them in, the commit grouping in section 3 is wrong.

Two are useful before you drop them. The linear-code linkback carries the Linear issue key, such as CW-771. The sentry-io and seer-by-sentry comments carry the Sentry issue and the Autofix link. That is how you find the upstream issue.

3 Group the commits around feedback

The script scripts/timeline.mjs does this with no model call. It merges the commits and the feedback events into one list, sorts by timestamp, and splits the commits at the first feedback event.

Add a fifth polarity: superseded

You said that a close is negative or neutral feedback. In 6 of the 25 closed PRs I sampled, you closed your own PR with a reason: "Superseded by #122900", "Landed directly on main as c0aa2ce", "Closing in favor of folding this into #121031".

Nobody rejected that code. It moved. If you score these as negative, the classifier learns the wrong lesson from a quarter of your closed PRs. I recommend a separate superseded outcome, treated as neutral and kept out of the bad set. Detect it when the closer is the author and the last human comment matches /superseded|landed directly|in favor of|folding into/i.

5 Stages, cheapest first

Every stage returns one small strict JSON verdict. The orchestrator keeps only that JSON. It never holds a diff or an issue body in its own context. That is how the context stays clean across many PRs.

Extra free exits

  • A PR with zero human comments that the author closed quickly returns undecided at stage 0. There is no feedback signal in it. Many of your closed PRs have this shape.
  • Cap the diff at 60 KB. Drop lockfiles, snapshots and generated files before you measure it.
  • Run stages 3, 4 and 5 in parallel once stage 2 passes. Stage 6 runs only when they disagree.

6 Why this plan has no embeddings

You offered to index the AGENTS.md files or ~/code/sentry-docs. I measured them. You do not need an index.

  • Both AGENTS.md files together are 12.7 KB. Put them in the prompt whole. An index would add a build step and a staleness risk for no gain.
  • The frontend-conventions skill already maps diff content to its rule docs with an exact regex table. That gate is free and precise. Semantic retrieval would be slower and would miss more.
  • ~/code/sentry-docs holds 5013 .mdx files, but this chain never asks a product question. Indexing it is work with no consumer.

Keep one fallback in reserve. If rule lookup ever grows too large, search the headings with ripgrep first. Add embeddings only if ripgrep is not enough.

6a What is built, and what the data corrected

harvest.mjs and timeline.mjs are written and run. The harvest pulled 299 PRs in 59 seconds with no failures, into a 5.5 MB cache that re-runs incrementally. Both are zx, and neither makes a model call.

Correction: evidence is two axes, not one

My first evidence score was a single number, and it was wrong. It gated out 42 PRs as "thin evidence" that were perfectly judgeable. It had conflated two different questions.

Coherence asks whether the ladder can run at all. It needs a description and a tractable diff. It does not need human comments. Reception asks how the PR landed, and needs comments, reviews and an outcome.

These come apart on real data. 44 PRs have a rich description — median 1558 characters — and a small diff of median 72 lines, but zero human comments. The description → code link runs on them fine. They are silent, not unjudgeable.

So only coherence gates. Low reception became a finding the classifier reports, never a refusal to decide. That single change cut the undecided rate from 19% to 9%, and the 9% that remains is 25 PRs with a literally empty description plus one oversized diff — a class with genuinely no intent statement to check the code against.

Correction: drop near-constant terms from any score

My first score gave weight to "the outcome is known". That is true for essentially every PR in a closed-PR corpus, so it added a constant offset and pushed 78% of PRs into a single band. A constant carries no information. Removing it spread the distribution into something usable.

This is the same fake-precision trap section 6 warns about, and I walked into it once before the data caught me. It is a good argument for keeping the arithmetic in code, where a histogram can expose it, rather than inside a prompt.

Scripts are zx, not bash, because you prefer that. To prove the classifier works, hand-label about 30 PRs across the four shapes: merged clean, merged after changes, closed and superseded, closed and abandoned. Then eval.mjs prints a confusion matrix and the cost per PR.

Aim for high precision on bad and needs-changes. A wrong good is the most expensive error. undecided is the safety valve you allowed, but treat it as a cost and track its share, so the classifier does not drift into refusing to decide.

8 Three decisions for you

Does superseded get its own label?
Recommended: yes. It covers about a quarter of your closed PRs, and scoring it as negative teaches the wrong lesson.
How large is the corpus?
Default if you say nothing: the getsentry org, 200 PRs you wrote plus 100 you reviewed.
Does "reviewed" include PRs where you only commented?
Default if you say nothing: yes. It uses --commenter as well as --reviewed-by.
